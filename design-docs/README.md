# Design Documents

## 1. 目的

本目录用于记录项目经过讨论、确认和整理后的需求、技术设计、开发计划及项目状态。

所有文档应保持简洁、明确、可执行、可追溯，避免歧义和重复定义。

测试报告、完整日志、事件记录和临时截图统一保存到项目根目录 `test-results/`，该目录由 Git 忽略，允许清理，不作为随仓库分发的正式设计文档。测试脚本应自动创建输出目录，本目录不保存测试产物。正式需求和状态文档只维护必要结论与未解决事项；指向 `test-results/` 的历史报告链接仅在本机产物仍存在时可用。

## 2. 文档结构

推荐采用以下结构：

```text
design-docs/
├── README.md
├── principles/
│   └── ai-development.md
├── requirements/
│   ├── overview.md
│   ├── modules.md
│   └── modules/
│       ├── module-a.md
│       └── module-b.md
├── architecture/
│   ├── overview.md
│   ├── database.md
│   ├── api.md
│   └── decisions/
│       └── ADR-001.md
├── plans/
│   ├── roadmap.md
│   └── phases/
│       ├── phase-01.md
│       └── phase-02.md
├── state/
│   ├── current.md
│   ├── issues.md
│   └── changelog.md
└── templates/
    ├── module-template.md
    ├── task-template.md
    ├── issue-template.md
    └── decision-template.md
```

以上是推荐结构，不是强制要求。可以根据项目规模合并、增加或省略文件，但应保持职责清晰，避免重复维护相同的信息。

### 2.1 各目录的职责

| 目录 | 职责 |
|---|---|
| `principles/` | AI 开发时必须遵守的通用行为规则 |
| `requirements/` | 项目目标、功能需求、业务规则和验收标准 |
| `architecture/` | 技术架构、数据结构、接口约定和重要技术决策 |
| `plans/` | 开发阶段、任务拆分、依赖关系和阶段验收要求 |
| `state/` | 当前开发进度、待处理问题和重要变更记录 |
| `templates/` | 新建模块、任务、问题和技术决策文档时使用的模板 |

### 2.2 主要文件的职责

| 文件 | 主要内容 |
|---|---|
| `README.md` | 本目录的管理规范、文档职责和维护规则 |
| `principles/ai-development.md` | AI 的工作方式、决策边界、测试要求、文档更新和任务汇报规则 |
| `requirements/overview.md` | 项目背景、目标、范围、非目标和总体需求 |
| `requirements/modules.md` | 功能模块清单、模块职责、模块之间的关系与边界 |
| `requirements/modules/*.md` | 单个模块的详细需求、业务规则、异常处理和验收标准 |
| `architecture/overview.md` | 技术栈、系统结构、模块依赖和架构约束 |
| `architecture/database.md` | 数据库表、字段、类型、约束、索引、关联关系和迁移要求 |
| `architecture/api.md` | API 或模块接口的参数、返回值、错误处理和兼容性要求 |
| `architecture/decisions/ADR-*.md` | 重要技术决策、备选方案、决策理由及影响 |
| `plans/roadmap.md` | 总体开发阶段、里程碑、依赖关系和阶段顺序 |
| `plans/phases/phase-*.md` | 阶段任务、前置条件、实施范围、测试和验收标准 |
| `state/current.md` | 当前阶段、正在处理的任务、已完成内容和下一步 |
| `state/issues.md` | 待确认需求、待调查事项、阻塞问题和待验证结论 |
| `state/changelog.md` | 重要需求、设计和计划变更的简要记录 |
| `templates/` | 对应文档的统一格式模板 |

实际项目不一定需要所有文件。若某项内容尚不存在，可以暂时不创建对应文件；当内容达到需要独立维护的复杂度时，再拆分文件。


## 3. 文档权威性

- 用户明确确认的需求和决策，是对应业务需求与设计的权威依据。
- 需求文档定义预期行为；架构文档定义技术实现约定；计划文档定义执行顺序；状态文档反映实际进度。
- 不同文档不得重复定义同一项细节，应优先引用其权威来源。
- 发现文档冲突、需求与设计冲突或设计与代码不一致时，必须识别并记录，不得静默选择或覆盖。
- 代码反映当前实现状态，不得因为代码现状而自动改变已确认的需求。

## 4. 需求讨论与确认

- 讨论中的想法、AI 建议、未验证假设和已确认结论必须明确区分。
- 用户没有明确确认的建议，不得视为已确认需求或设计决策。
- 关键歧义应记录在 `state/issues.md`，并在相关开发开始前解决。
- 新需求或变更应先分析影响范围，再更新相关文档。
- 影响已确认需求、架构、数据库或接口的重大变更，必须先获得用户确认。

## 5. 文档更新规则

- 修改前先读取相关文档，检查现有内容和依赖关系。
- 只修改受到本次讨论或变更实际影响的文档。
- 同步更新必要的交叉引用、任务计划和项目状态。
- 删除或替换已有设计前，应确认其不再适用，避免丢失重要约定。
- 文档内容应记录当前有效结论，不复制冗长聊天记录。
- 已确认的关键决策应记录决策内容、原因、影响和状态。
- 计划完成后将有效行为并入模块文档并移除计划。

## 6. 文档状态

文档中的关键事项应根据实际情况标注：

- `草稿`：正在讨论或整理，尚未确认。
- `待确认`：需要用户决定。
- `已确认`：已获得用户明确确认。
- `待验证`：结论仍需要调查、实验或测试验证。
- `已废弃`：不再适用，仅保留必要的历史记录。

文档状态不能代替具体内容的确认状态。一个文档可以整体已确认，但仍包含明确标记的待验证事项。

## 7. 开发前检查

开始正式开发前，应确认：

- 项目目标、范围和非目标明确。
- 需要开发的模块及其边界明确。
- 关键业务规则和验收标准明确。
- 影响开发的关键技术决策已经确认。
- 关键接口和数据结构已定义，或已明确允许延后设计的范围。
- 开发阶段、任务依赖和测试要求明确。
- 阻塞问题已解决，非阻塞遗留事项已明确记录。

如果仍存在影响当前任务的关键不确定事项，不得直接开始相关开发。

## 8. 维护原则

保持文档简洁、单一职责、引用清晰。

简单项目可以合并文档或省略不适用的文件；复杂项目可以增加独立模块规格、接口文档或专项设计，但必须明确其职责，避免重复定义。
